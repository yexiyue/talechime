# Kokoro + g2pW：M4 Pro 官方对照与 RTF（2026-10-27）

本机实测。官方 CPU 与原生 CPU 的配对组均使用 F32、相同文本、分段、音色和语速；
开启 g2pW 时，每个分段的最终音素、全部整数时长预测和 PCM 样本数在双方所有轮次完全一致。
原生 CPU 在本轮仍慢于官方 Python；Metal 混合路径的平均耗时也没有优于原生 CPU。

## 设备、来源与条件

- Apple M4 Pro，12 核 CPU / 16 核 GPU，24 GiB 统一内存；macOS 26.6.2（25G83），接交流电。
- Rust 1.99.0，release / LTO；Candle 为工作区固定 0.11 fork，CPU 使用 Accelerate。
- 官方 PyTorch 2.7.1、Transformers 4.51.3；双方 ORT 1.28.0 CPU，g2pW intra threads=2、sequential、graph optimization all。
- `VECLIB_MAXIMUM_THREADS=4`、`RAYON_NUM_THREADS=4`、`OMP_NUM_THREADS=4`、`OPENBLAS_NUM_THREADS=4`；官方 Torch intra=4、inter=1。未测逐算子的实际工作线程数。
- Kokoro 0.9.4 `dfb907a02bba8152ca444717ca5d78747ccb4bec`；Misaki 0.9.4 `fba1236595f2d2bf21d414ba6e57d25256afada3`。
- g2pW 作者源码 `b9328ce8129c4717a70f16a2688542a0197541dd`，作者 v2 ONNX，窗口 32、batch 32。模型、词表和许可证来源见 [SOURCE.md](../../../crates/kokoro/SOURCE.md)。
- 声学权重为官方 Kokoro-82M-v1.1-zh 固定版本 `01e7505bd6a7a2ac4975463114c3a7650a9f7218`；音色 `zf_001`、speed=1.0、24 kHz 单声道。
- 原生端使用开发期折叠 weight normalization 的 F32 权重；官方端直接执行原始 `KModel`，没有修改声学代码，没有 trace、compile 或量化。
- 官方 Kokoro/Misaki 原版没有 g2pW 开关。表中的“官方 + g2pW”是本地适配组合：作者官方 `G2PWConverter` → 官方 Misaki（仅在变调/儿化之前覆盖多音字声韵母）→ 官方 `KModel`。不是上游直接发布的集成产品。

## 计时边界与重复协议

每个配置 3 个独立进程，每个进程对每个样本先预热 1 轮，再记录 5 轮热合成。
共 15 个进程、180 次请求，其中 150 次为热轮。按三批串行执行，第二批反转 CPU 配置顺序；没有并发运行本任务的推理进程。
每个进程保留逐轮值和均值；表中是三个进程均值的均值。RTF 使用实际合成总秒数 / 实际音频总秒数，不平均分段 RTF。

- 短句 21 字符：`银行行长还没有回来，他要先把书还给单先生。`，1 段。
- 多音字试听原稿 252 字符，按原生前端 180 音素预算冻结为 6 段；两端逐段使用完全相同原文。
- 包含文字规范化、g2pW（开启时）、分词、变调、儿化、音素映射、IDs/style 选择、随机激励、声学推理和主机 PCM 读取；保留有限值校验。
- 排除模型准备/加载、预先冻结分段方案、文件导出、音频播放。组件总计时包含少量记录与校验开销。
- 每段 seed=7；Torch 与 Rust 的随机数序列不同，因此没有声称 PCM 逐位相同。本轮核对音素、整数时长和长度，未为这两段语料新增跨框架 PCM SNR 验收。
- Metal 为 CPU 编码/韵律/F0/FFT + Metal 解码器；g2pW 仍在 CPU。计时包含 PCM 回到主机后的读取，不是 GPU enqueue 耗时。

## 配对组件结果

RTF 越低越快；RTF < 1 表示生成速度超过实时。范围是三个进程各自热轮平均 RTF 的最小值至最大值，不是置信区间。

| 配置 | 语料 | 音频秒数 | 合成均值 / 秒 | RTF | 进程均值 RTF 范围 |
| --- | --- | ---: | ---: | ---: | --- |
| 官方 Python CPU，原版 | 短句 | 5.200 | 0.3743 | 0.07199 | 0.07086–0.07267 |
| 官方 Python CPU，原版 | 试听原稿 | 53.650 | 3.8180 | 0.07117 | 0.07001–0.07342 |
| 原生 CPU，原版 | 短句 | 5.200 | 0.9480 | 0.18231 | 0.18087–0.18488 |
| 原生 CPU，原版 | 试听原稿 | 53.650 | 9.7813 | 0.18232 | 0.18145–0.18326 |
| 官方 Python CPU + g2pW 适配 | 短句 | 5.175 | 0.4690 | 0.09063 | 0.08415–0.10269 |
| 官方 Python CPU + g2pW 适配 | 试听原稿 | 53.500 | 4.4098 | 0.08243 | 0.07945–0.08831 |
| 原生 CPU + g2pW | 短句 | 5.175 | 1.0344 | 0.19989 | 0.19504–0.20943 |
| 原生 CPU + g2pW | 试听原稿 | 53.500 | 10.6195 | 0.19850 | 0.18977–0.20767 |
| 原生 CPU+Metal + g2pW | 短句 | 5.175 | 1.0809 | 0.20887 | 0.20346–0.21809 |
| 原生 CPU+Metal + g2pW | 试听原稿 | 53.500 | 10.9618 | 0.20489 | 0.19947–0.21472 |

试听原稿开启 g2pW 后，原生 CPU 的 RTF 为官方 CPU 适配组合的 **2.41 倍**，也就是当前原生实现较慢；原生约 **5.04 倍实时**。
原生 CPU 开启前后 RTF 从 0.18232 到 0.19850，观察增幅约 8.9%。开关会改变读音和输出时长，且存在后台负载波动，不能把全部增幅精确归因于 g2pW 本身。

| 配置 | 中文前端 / 秒 | 声学与主机 PCM / 秒 | 总耗时 / 秒 |
| --- | ---: | ---: | ---: |
| 官方 Python CPU + g2pW 适配 | 0.5937 | 3.8149 | 4.4098 |

原生原版前端约 4.4 ms，开启消歧后约 628.3 ms。开启组整个中文前端约占总合成时间的 5.9%。
双方前端耗时接近，主要性能差距在声学阶段；没有进一步的算子 profiler 证据，不能把差距指定到某一个卷积或 LSTM 算子。

## 公共 Engine 实际交付

另外对当前公共 `Engine::synthesize_with_options` 运行 1 个独立进程、1 次预热 + 5 次热合成，使用相同试听原稿、CPU、`1.1-zh-g2pw`、`zf_001`、固定请求 seed=7。
计时从调用合成接口开始，持续接收直到显式 Completed；检查所有 PCM 为有限值。包含生产分段、seed 派生、边界静音处理、响度对齐和通道交付；不含模型准备和播放。

| 指标 | 结果 |
| --- | ---: |
| 热合成均值 | 10.6652 s |
| 实际交付音频 | 48.810 s |

## 环境波动与复现证据

未锁频，也没有关闭用户其他任务。观察到 StorageManagement、外部 rustc/Clippy/链接及其他桌面进程；第三批部分原生长文热轮约从 10 秒波动到 12 秒。
所有预定热轮均保留，没有剔除较慢轮次。批量执行的 14 个进程在启动前记录后台进程和 `pmset -g therm`；最先单独执行的 CPU 开启组另保留运行中后台快照。启动等待不进入 RTF。上述结果是这台共享机器的观察，不代表安静机器的绝对上限或跨平台性能。

## CPU 性能差距定位（同日追加）

对相同试听原稿的 6 段已冻结 g2pW 音素单独测声学模型。每个诊断探针 1 次预热 + 3 次热轮，保持同机、F32、线程和 seed 条件。
原生探针复制同一模型代码并只插入时间戳/作用域计时；算子模块读取生产源码或仅增加计时 guard 的副本。官方探针对原始 forward 增加时间戳，并对原始模块添加 CPU 前后 hook。 官方 Conv hook 计时位于已有 weight-norm 前置 hook 之后，卷积行对应纯卷积模块主体；粗阶段总计时仍包含原始模型的全部运行期开销。
没有更换算法或模型参数；三个原生诊断探针的首段 PCM 均与公共模型库逐样本浮点值相等，其余分段长度均与配对数据一致。
这些是单进程诊断，会有插桩和环境开销，不覆盖前面的 15 进程 RTF 基线，也不构成优化收益验收。

粗阶段探针：原生声学总计 9.2818 s，官方 3.7291 s；其中原生解码/激励 8.6986 s，官方 3.3687 s，约 96.0% 的额外耗时出现在这一阶段。
原生上采样生成器所在区间单独约 8.36 s，占声学总耗时约 90%；据此再拆算子，而非把 LSTM 当成主因。

### 原生普通卷积的内部耗时

下列时间已包含在普通卷积总耗时中，不与上表相加。

| 子阶段 | 耗时 / 秒 |
| --- | ---: |
| 复制输入、权重和 bias | 0.0958 |
| 输出分配及 bias 初始化 | 0.0464 |
| 分配、清零并逐点展开卷积窗口 | 4.7111 |
| Accelerate GEMM | 1.2673 |

主要问题落在 `blas::conv` 的窗口展开：每次重新分配 columns，用通道 × kernel × 输出位置的三重循环，逐点计算位置、检查边界并复制。该 CPU 路径对带 bias 的 1×1 卷积也会构造 columns；已有 Accelerate GEMM 只覆盖后面的乘法。
本轮展开约占原生普通卷积时间的 77%，权重/输入复制本身约 0.10 s，不能把复制成本误报为主因。
InstanceNorm 的原生路径先复制 Tensor 到 Vec，再按 batch/channel 串行统计均值、方差并执行 affine，保留官方 F32 舍入语义。其开销约 1.29 s，官方相同 70 个模块约 0.41 s。
LSTM 的逐步张量运算与重复权重复制确有额外开销，但本轮累计约 0.30 s，官方约 0.14 s，其优先级低于窗口展开和归一化。
源码位置：[CPU 卷积](../../../crates/kokoro/src/blas.rs)、[归一化和 LSTM](../../../crates/kokoro/src/ops.rs)。
后续优先验证 stride=1 的连续片段复制与零区处理、1×1 直达 GEMM、columns/输出缓冲复用，再处理 InstanceNorm 的 SIMD/并行实现；所有候选仍须保持现有官方数值门槛并重测完整 RTF。未实施这些优化，也不预报具体收益。
本次只定位 CPU；没有用这些 CPU 插桩结果解释 Metal 的具体 GPU kernel 性能。
